# 实际项目升级误报修复

用户反馈：0.45→0.47 在已有项目中集中报出模板章节删除／重叠冲突，中文原因乱码。上一轮测试通过并没有覆盖此类“旧版初始化＋多次部分升级＋事实文档重写”的组合，这是覆盖缺口。

确认的原因：

- 基线仅按原始 bytes 匹配，LF／CRLF／BOM 差异及旧安装生成的 checksum 导致原模板被误判为用户定制。
- 历史目录只收集 tag 中的模板，遗漏已发布 migration 的实际 incoming／baseline 素材。
- 项目事实成稿被套用规则文件的章节约束，用户正常替换占位章节被误判为冲突。
- 上层强制按 UTF-8 读取子进程，但 Windows 子进程默认输出本地编码；errors=replace 掩盖了乱码。
- 前置冲突后继续尝试同一文件，产生重复级联错误；界面先列 write/remove，未明确这些只是计划。

修复：对可验证历史模板做 BOM／换行等价匹配，并收录历史迁移素材；33 个事实 owner 使用显式白名单保留整份本地成稿，治理、Skill、入口继续检查真实冲突；同一失败文件只报首个冲突；JSON 子进程显式 UTF-8 且严格解码；中文预检、计划动作和实际应用区分显示。

真实项目验证始终只读：预检 ready、0 conflicts，28 份事实文档与 6 个定制章节保留。在 D:\tmp 隔离副本应用成功，逐份确认原事实内容仍存在（仅允许已声明的旧链接变更）；再次逐字节检查真实项目全部计划输入，文件未改变，state 仍为 0.45.0。没有将项目内容复制进本仓库测试素材。

回归新增：成稿替代模板章节、事实策略不能用于治理 owner、历史 checkout 和 migration 独有素材、CP936 父进程的中文冲突输出。16 项 migration 测试通过，日志 reported-upgrade-tests.log。

独立只读审查 pass：实际项目预检零冲突；BOM＋CRLF 下的真实入口／治理／Skill 重叠修改仍阻断；把 project_facts 强加给这些规则文件被白名单拒绝；事实成稿结构完整保留。复核 structured_upgrade.py SHA256：`D9B43F684D1C97D623135277AD309A8A7DEBE547F844333198FCD11696030024`。
